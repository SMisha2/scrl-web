# ScRl Web

ScRl — общая платформа школьной взаимопомощи. Интерфейс остаётся статическим сайтом GitHub Pages, а общие аккаунты и данные хранятся в Supabase.

## Что работает в проекте

- Регистрация по email и паролю с подтверждением адреса кодом.
- Общий профиль, ФИО, класс и роли ученика, учителя и администратора.
- Общие кошельки ScRl и V-RUB, журнал операций и резервы.
- Доска запросов и предложений, категории, поиск и отклики.
- Маркет услуг и количество свободных заказов.
- Сделки с серверным резервом ScRl, перепиской, выполнением, подтверждением и спорами.
- Биржа двух учебных единиц с резервом средств, встречными заявками, расчётом комиссий и историей.
- Раздел аукционов для неденежных школьных призов: ставки, возврат перебитой ставки и завершение.
- Избранное, жалобы, уведомления, отзывы и история активности.
- Кабинет учителя с проверкой класса и недельным лимитом начислений.
- Администрирование: роли, блокировки, обезличивание, модерация, аудит и сводная статистика.
- Автоматическая отправка подозрительных публикаций на ручную проверку по базовым правилам.

## Сервисы

- Сайт (канонический адрес): https://www.scrl.site/
- Короткий адрес https://scrl.site/ автоматически перенаправляется на канонический.
- Репозиторий: https://github.com/SMisha2/scrl-web
- Supabase project: `scrl-production` (регион Frankfurt, project ref `bkmccvazgnfnjefrytki`).

## Первый запуск

1. Открой сайт и создай личный аккаунт на странице регистрации.
2. Подтверди email-кодом из письма, затем войди с тем же email и паролем.
3. Первый администратор назначается автоматически только после входа с подтверждённой почтой владельца проекта. В его профиле можно временно выбрать интерфейс ученика или учителя; реальная роль администратора в базе не меняется и при новом входе восстанавливается. Целевая почта хранится в закрытой схеме Supabase; одноразовый код в браузере не используется.
4. После назначения администратора он сможет назначать учителей и управлять участниками.

Для этого проекта первичный адрес администратора уже привязан в закрытой таблице Supabase. Сначала зарегистрируй его через сайт и подтверди почту.

Новый аккаунт получает 100 ScRl и 50 V-RUB в качестве учебного стартового баланса. Профили, кошельки, сделки и публикации общие для всех авторизованных пользователей. При удалении аккаунта свободные остатки списываются из кошелька; ScRl отражаются как сожжённые, V-RUB исключаются из расчёта активного предложения, а журнал сохраняется обезличенным. Старые локальные демо-аккаунты и записи из localStorage в production не используются и не переносятся.

## Пилот в школе

Перед запуском на реальных данных школа должна назначить ответственного взрослого и определить свою роль как оператора персональных данных. Пошаговый чек-лист, схема ролей и границы пилота — в [docs/school-pilot.md](docs/school-pilot.md).

Коротко: один класс, учебные баллы без реальных денег, человеческая модерация, российский хостинг и SMTP, отключённые внешние ИИ-сервисы для реальных данных. Юридические страницы в `legal/` пока являются черновиками и требуют финального согласования.

## Безопасность и границы

- RLS включён на таблицах публичной схемы. Чтение и изменение строк ограничены правилами доступа.
- Балансы, резервы, начисления, ставки и расчёты сделок выполняются серверными SQL-функциями. Прямое изменение баланса и роли из браузера запрещено.
- Пользователи видят только собственные финансовые записи; администратор — сводную информацию, а учитель — ограниченные данные своего класса.
- Email других пользователей не публикуется в общем списке.
- ScRl и V-RUB — учебные виртуальные единицы, а не реальные деньги. Пополнение и вывод реальных денег не реализованы.
- В школьных аукционах разрешены только неденежные призы. Не используй реальные данные учащихся до согласования проекта ответственным взрослым и школой.
- Проверка пользовательского содержимого выполняется через Edge Function `scrl-moderation`. Когда одновременно включены `SCRL_MODERATION_ENABLED=true`, `SCRL_MODERATION_EXTERNAL_PROCESSING_APPROVED=true` и настроен `GROQ_API_KEY`, нормализованные тексты публикаций, услуг, аукционов, сделок, сообщений, отзывов, профилей, жалоб и оснований начислений передаются Groq для классификации. Не отправляй пароли, адреса и другую лишнюю личную информацию.
- При выключенной внешней модерации новые проверяемые действия останавливаются, а не обходят проверку. Решения `flag` и `hide` отправляются в очередь ручного разбора; автоматическая блокировка ограничена критическими категориями и высоким порогом уверенности. Пользователь может подать апелляцию.
- Отдельная Edge Function `scrl-ai` формирует административные сводки только по фиксированным агрегированным числам. Она не предназначена для чтения личных сообщений или публикаций.

## Важное ограничение email

Встроенная отправка писем Supabase предназначена только для тестирования: письма уходят только на адреса участников организации и ограничены двумя сообщениями в час. Для регистрации всего лицея нужно настроить собственный SMTP в Supabase Authentication. Не отключай подтверждение email ради обхода этого ограничения.

В production (`scrl-production`) SMTP настроен на внешнего провайдера (школьный домен `euploading.com` через сервис-провайдер); отправленные письма с кодом подтверждения проверены и доходят до пользователей. Письма нового провайдера не должны попадать в чат и не должны добавляться в GitHub.

Экран подтверждения принимает код из 6–8 цифр: конкретная длина зависит от настроек Supabase Auth. Открой **Authentication → Email Templates → Confirm signup** и проверь, что письмо выводит значение `{{ .Token }}` (а не только ссылку `{{ .ConfirmationURL }}`). Пример тела письма:

```html
<h2>Подтверждение ScRl</h2>
<p>Введи этот код на сайте: <strong>{{ .Token }}</strong></p>
```

Затем открой **Authentication → SMTP Settings** и укажи SMTP-данные почтового провайдера, которым разрешено пользоваться школе. Не отправляй пароль SMTP в чат и не добавляй его в GitHub. См. [руководство Supabase по SMTP](https://supabase.com/docs/guides/auth/auth-smtp) и [руководство по OTP](https://supabase.com/docs/guides/auth/auth-email-passwordless).

## Внешний AI Moderator

Функция `supabase/functions/scrl-ai/index.ts` принимает только один из фиксированных типов отчёта и список числовых агрегатов. Свободный вопрос администратора и личные данные не отправляются провайдеру. Это отдельный сервис от `scrl-moderation`, которая при включённой и согласованной настройке проверяет пользовательский текст через Groq.

1. В Supabase Dashboard открой **Edge Functions → Secrets**.
2. Добавь `SCRL_AI_API_KEY` в Edge Function Secrets. По умолчанию используется OpenRouter с автоматическим выбором доступной бесплатной модели: `https://openrouter.ai/api/v1` и `openrouter/free`. При необходимости можно переопределить их через `SCRL_AI_API_URL` и `SCRL_AI_MODEL`.
3. Включи `SCRL_AI_ENABLED=true` и `SCRL_AI_EXTERNAL_DATA_APPROVED=true` только после согласования внешней обработки агрегированных данных со школой и ответственным взрослым. При необходимости задай `SCRL_AI_ALLOWED_ORIGIN=https://www.scrl.site`.
4. При отсутствии ключа или согласования приложение оставляет локальный отчёт. API-ключ хранится только в Edge Function Secrets и не попадает в HTML, JavaScript или GitHub.

У бесплатных моделей OpenRouter есть ограничения по числу запросов и доступности; гарантированно безлимитного бесплатного API нет. Edge Function остаётся совместимой с другими провайдерами формата OpenAI Chat Completions.

## Файлы

- `index.html` — экран входа и навигация.
- `css/style.css` — базовые стили и наследие классов.
- `css/design.css` — дизайн-система поверх стилей: токены темы, каркас, компоненты, адаптив. Правила находятся в `@layer scrl-design`.
- `js/app.js` — страницы, форма и действия.
- `js/backend.js` — клиент общей базы и REST/RPC-вызовы.
- `js/core.js` — чистые расчёты экономики.
- `js/config.js` — URL и публичный ключ Supabase.
- `supabase/schema.sql` — legacy bootstrap для старой схемы профиля. История SQL-миграций отслеживается в `supabase/migrations/`; перед восстановлением на новой базе проверь цепочку на отдельном тестовом проекте.
- `tests/` — автоматические проверки.
- `.github/workflows/deploy-pages.yml` — проверка синтаксиса, тесты и публикация GitHub Pages.

## Проверка

GitHub Actions выполняет:
- `node --check` для браузерного JavaScript и Service Worker;
- `deno check` для трёх Supabase Edge Functions;
- регрессионные тесты `node --test tests/*.test.cjs`;
- перед публикацией GitHub Pages повторяет проверки и проверяет HTTPS-домены.

Локальный запуск проверок:

```sh
node --check js/config.js
node --check js/core.js
node --check js/backend.js
node --check js/app.js
node --check sw.js
node --test tests/*.test.cjs
deno check supabase/functions/scrl-account/index.ts
deno check supabase/functions/scrl-ai/index.ts
deno check supabase/functions/scrl-moderation/index.ts
```

## Ограничения самостоятельного развёртывания

- Базовые миграции production-схемы `20261116005525`–`20261116010448` сейчас не хранятся в этом репозитории. Последующие миграции здесь есть, но их недостаточно для создания пустой базы. Не запускай `supabase db reset` на production и не считай репозиторий автономным источником восстановления БД. До независимого развёртывания нужно экспортировать и проверить базовую схему и историю миграций из действующего Supabase-проекта.
- GitHub Pages workflow публикует только статический сайт. Он проверяет Edge Functions через `deno check`, но не развёртывает их в Supabase. Изменённые функции нужно отдельно публиковать через Supabase CLI или Dashboard.
- CI не имеет доступа к закрытым Supabase Secrets и production-данным, поэтому не подтверждает фактическую работу SMTP, настроек Auth, RPC, RLS и внешних ключей. Эти настройки нужно проверять в самом Supabase-проекте.
- Автоматические тесты не заменяют сквозной тест регистрации, подтверждения email, входа, восстановления пароля, операций с балансом, сделок, модерации и администрирования на отдельной тестовой учётной записи.

Для пилота со школьниками дополнительно выполни требования из [чек-листа школьного пилота](docs/school-pilot.md). До назначения взрослого оператора и согласования обработки данных не используй реальные данные учеников.


## Безопасное применение миграций

Наличие migration-файла в GitHub не означает, что он уже применён к production Supabase. Перед изменениями production:

1. Сделай резервную копию базы и проверь возможность восстановления.
2. Сравни версии файлов в `supabase/migrations/` с `supabase_migrations.schema_migrations` в целевом проекте.
3. Примени ещё не применённые миграции сначала на отдельной тестовой базе.
4. Проверь регистрацию, RLS, RPC, резервирование, сделки, биржу и удаление тестовых данных.
5. Только после этого планируй отдельное production-обновление.

Не запускай `supabase db reset` или безусловный `db push` на production.
